# 待决项与交付顺序

状态：用于后续对话和排期，不是已经承诺的开发日历。当前已经整理主体规则与交互草案，但用户尚未确认所有界面和实现边界，不开始新规则编码。

## 1. 先确认会导致返工的问题

这些问题优先于小游戏细节、额外操作模式和装饰性界面。先在具体使用流程中确认，不逐个询问所有配置数值。

| ID | 要确认的内容 | 为什么影响主体 | 当前状态 |
|---|---|---|---|
| C01 | 日程能否留空、同活动能否重复、额外材料何时校验和扣除 | 决定日程草稿、确认和顺序执行行为 | 待定 |
| C02 | 多建筑争用材料、缺料时整单停产还是部分生产、是否需要预留 | 决定生产预测与真实结算能否一致，也影响卖出、送礼与培养 | 待定 |
| C03 | 洞天格制与占地、道路邻接、断路状态、民居容量下降后的处理 | 决定放置、移动、御灵工作和产出是否合法 | 待定 |
| C04 | 主线触发后何时完成、同时满足多个升级如何处理、具体互斥和成本拆分 | 防止高继承属性跳剧情、重复扣费和重复奖励 | 待定 |
| C05 | 首版允许保存的阶段，以及冒险中途如何恢复 | 决定需持久化哪些状态，不默认任意时刻保存 | 待定 |
| C06 | 基础内容最小清单：日程、建筑、配方、御灵、主线数量 | 没有清单无法判断主体范围、内容量和时间 | 待定 |

确认 C01 至 C05 时优先选择直接、确定、少分支的规则；不以更通用的配置表达式替代尚未作出的设计决定。

## 2. 再确认主要界面

建议按一次完整回合依次审阅：

1. 养成主界面：女儿状态、自由活动、日程是否各自清楚；不展示具体年龄、年月。
2. 洞天：放置与移动、生产设置、御灵分配、当前库存与预测是否容易区分。
3. 确认与结算：闲置提示能否返回，培养与生产是否顺序清楚，新的解锁何时可用。
4. 人物与冒险：配置是否复用，物品是否只需一次点击，队友是否避免等级焦虑。
5. 开局继承与结局：土地、图纸、故事是否独立，人生结果与结缘结果是否分开。

02 文档是信息与流程草案，不是已经制作好的视觉原型。下一轮只需先审主界面与一个回合走查，不同时设计所有页面。

## 3. 可配置但需要最终取值的内容

- 精力上限、活动成本、基础日程与特殊日程的成长和压力变化。
- 建筑占地与成本、配方数量、御灵适应性映射、景观距离曲线、产出取整。
- 剧情属性阈值、解锁条件、升级成本和三个阶段的表现资源。
- 物价、商店库存与可购买御灵范围。
- 战斗属性转换、功法优先级、冷却、倒地与复活、道具目标比较。
- 冒险节点权重、各目的地种子派生、第二次出发与 Boss 套组的读档策略。
- 成就继承成本、互斥、预算；人生与结缘结果的具体条件与优先级。

这些表不要求本轮填满。先为最小可走通的内容给试算值，注明假设，再随主体试玩调整。不要为了配置便利开发专用编辑器。

## 5. 交付顺序提案

只有用户确认主体与交互准备度后，才进入编码。代码以 Godot 常规目录组织，可以重写旧原型，不安排旧架构兼容阶段。

| 阶段 | 交付物 | 完成判据 |
|---|---|---|
| D0 设计收敛 | 本目录、关键待决项决定、主界面交互定稿、最小内容表 | 用户认可主体意图，规则没有关键矛盾；当前仍在此阶段 |
| D1 培养回合 | A/B、培养槽、自由精力、压力、固定回合顺序、最小界面 | 能安排、确认并连续走完回合，成长只结算一次 |
| D2 洞天闭环 | 地块与道路、生产、御灵、库存、清心草与加工链 | 能走通“培养 -> 生产 -> 下一回合消耗支持培养” |
| D3 剧情与继承 | 节点前置、三阶段表现选择、父亲恢复、独立解锁、开局继承 | 能走通不同洞天进度与继承组合，不重复升级扣费 |
| D4 冒险与结局闭环 | 最小路线、半即时战斗、伙伴配置、物品、关键掉落、路线结局 | 能走通“洞天制品 -> 冒险 -> 剧情解锁 -> 洞天”与结局收束 |
| D5 内容与调优 | 扩充已批准的日程、角色、剧情与素材，平衡完整周目 | 验证实际时长、一周目压力和多周目爽感 |
| 后续增强 | 轻量小游戏与确有需求的便利功能 | 不延误主体，不默认扩成四个独立完整小游戏 |

这是工作包的先后关系，不是四艺等数值系统全部留到最后。比赛奖励、图纸和称号与主体解锁链一同设计，复杂操作部分可以后置。

验证阶段允许使用明确标注的测试数据走通奖励链，但不能把测试入口描述为已完成的比赛玩法，也不因此增加正式“快速比赛”模式。

## 6. 排期方法

暂不填写日历日期和“几天做完”的承诺。先确定 D0 的内容规模，再按四类工作估算：

- 核心程序与交互。
- 配置与剧情文本。
- 美术、动画、音频。
- 主体走查与必要修复。

需要补齐实际投入人数、每周可用时间、素材采用占位还是正式资源。每个工作包给区间与依赖，不为锦上添花功能预留与主体同量级的程序和测试预算。

主线文本与立绘按三阶段实际份数计算，不能只按逻辑节点数报内容工时。

## 7. 最小验证范围

核心规则重点验证：

- 培养槽与自由精力不混扣，A/B 查询口径正确。
- 压力按顺序影响概率，边界不漏档。
- 生产不使用本批次新产出；缺料规则、御灵唯一岗位和道路条件一致。
- 日程确认、剧情升级、奖励领取不重复扣除或发放。
- 土地、图纸、故事互不替代，三阶段表现不重复完成同一节点。
- 选定保存边界内能够恢复真实进度，不重新生成已经开始的冒险地图。

界面做少量真实流程走查，不为每种建筑、物品、小游戏参数组合制作独立测试场景。非核心玩法只验证开始、结束、计分、成本和奖励等必要行为。

本轮只有 Markdown 文档检查，没有运行游戏或新规则测试，也不声称上述验证已通过。
