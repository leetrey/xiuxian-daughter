## 2. 再确认主要界面

建议按一次完整回合依次审阅：

1. 养成主界面：女儿状态、自由活动、日程是否各自清楚；不展示具体年龄、年月。

## 5. 交付顺序提案

后续新增规则在确认边界后分段实现；已授权的试作范围见 05。代码按 Godot 常规目录组织，先完成可验证的主体闭环。

| 阶段 | 交付物 | 完成判据 |
|---|---|---|
| D0 设计收敛 | 本目录、关键待决项决定、主界面交互定稿、最小内容表 | 用户认可主体意图、关键边界和最小内容；当前仍需继续收敛 |
| D1 培养回合 | A/B、培养槽、自由精力、压力、固定回合顺序、最小界面 | 能安排、确认并连续走完回合，成长只结算一次 |
| D2 洞天闭环 | 地块与道路、生产、御灵、库存、清心草与加工链 | 能走通“培养 -> 生产 -> 下一回合消耗支持培养” |
| D3 剧情与继承 | 节点前置、三阶段表现选择、父亲恢复、独立解锁、开局继承 | 能走通不同洞天进度与继承组合，不重复升级扣费 |
| D4 冒险与结局闭环 | 最小路线、半即时战斗、伙伴配置、物品、关键掉落、路线结局 | 能走通“洞天制品 -> 冒险 -> 剧情解锁 -> 洞天”与结局收束 |
| D5 内容与调优 | 扩充已批准的日程、角色、剧情与素材，平衡完整周目 | 验证实际时长、一周目压力和多周目爽感 |
| 后续增强 | 轻量小游戏与确有需求的便利功能 | 不延误主体，不默认扩成四个独立完整小游戏 |

这是工作包的先后关系，不是四艺等数值系统全部留到最后。比赛奖励、图纸和称号与主体解锁链一同设计，复杂操作部分可以后置。

验证阶段允许使用明确标注的测试数据走通奖励链，但不能把测试入口描述为已完成的比赛玩法，也不因此增加正式“快速比赛”模式。

## 6. 排期方法

暂不填写日历日期和“几天做完”的承诺。先确定 D0 的内容规模，再按四类工作估算：

- 核心程序与交互。
- 配置与剧情文本。
- 美术、动画、音频。
- 主体走查与必要修复。

需要补齐实际投入人数、每周可用时间、素材采用占位还是正式资源。每个工作包给区间与依赖，不为锦上添花功能预留与主体同量级的程序和测试预算。

主线文本与立绘按三阶段实际份数计算，不能只按逻辑节点数报内容工时。

## 7. 最小验证范围

核心规则重点验证：

- 培养槽与自由精力不混扣，A/B 查询口径正确。
- 压力按顺序影响概率，边界不漏档。
- 生产不使用本批次新产出；缺料规则、御灵唯一岗位和道路条件一致。
- 日程确认、剧情升级、奖励领取不重复扣除或发放。
- 土地、图纸、故事互不替代，三阶段表现不重复完成同一节点。
- 选定保存边界内能够恢复真实进度，不重新生成已经开始的冒险地图。

界面做少量真实流程走查，不为每种建筑、物品、小游戏参数组合制作独立测试场景。非核心玩法只验证开始、结束、计分、成本和奖励等必要行为。
