# 核心实体与工程方案

状态：实体字段与实现方式为提案。本文件将“实体方案”具体化为业务数据、生命周期与归属，不意味着每个实体都要建一个脚本、数据库表或管理器。本轮只整理文档。

工程约束已按最新要求简化：旧工程由 vibe coding 生成，旧代码只作参考，不是必须沿用的架构。只保留简洁的 Godot 常规目录组织，不为旧实现增加迁移或兼容负担。

## 1. 最小实现原则

继续使用 Godot，不换引擎，不引入服务端、数据库、ECS 或通用规则 DSL。后续可根据新规则重写旧代码，不要求保留旧类、函数、Autoload 数量或调用链。

- 配置描述可调整的内容，本局状态记录玩家已经做出的选择。
- 界面提交操作，规则层检查并结算，状态层保存结果。
- 相同规则共用一处实现，尤其是 A/B 口径、库存扣除、生产预测和实际结算。
- 可以先用字典、数组和少量 GDScript 组织数据；仅在确有重复与复杂度时增加类型或模块。
- 配置格式暂建议 JSON 配合中文字段说明。格式尚待确认，不把“配置化”当作所有逻辑都必须写成数据表达式。
- 辅助玩法共用参赛、计分、奖励逻辑，不为不同比赛各建一套状态和存档系统。

## 2. 配置、状态与展示的边界

| 层 | 示例 | 是否存入本局档 |
|---|---|---|
| 配置定义 | 活动收益、配方、建筑占地、剧情条件、技能参数 | 通常保存引用 ID，不复制整份配置 |
| 本局状态 | A、库存、建筑位置、工作分配、剧情完成记录 | 是 |
| 周目外状态 | 已完成成就、可用继承预算、可选继承项 | 与本局分开保存 |
| 运行时派生值 | B、四维汇总、道路连通、产出预测、战斗面板 | 优先重算，不作为第二份真值 |
| 界面临时状态 | 当前页签、悬停预览、未确认移动位置 | 一般不存；保存边界待定 |

所有配置使用稳定 ID，相互引用 ID 而不是中文显示名。可读名称、描述和表现资源与数值规则分离，避免改文案使存档失效。

这里只要求最基本的配置版本标识与引用校验，不先开发跨多个历史版本的自动存档迁移框架。

## 3. 核心实体表

以下是概念实体，不是一实体一文件的建模清单。

| 实体 | 最小数据 | 归属与关键约束 |
|---|---|---|
| 成就档案 MetaProfile | 已达成成就、可选继承项 | 周目外；预算由成就规则计算，不由 UI 随意增加 |
| 开局选择 RunSetup | 本局选择的继承项、点数分配 | 开局确认后生成状态，不改其他局 |
| 本局 RunState | 内部回合、成长阶段、当前流程阶段、结束状态、子状态集合 | 新局建立，结局封存；不复用旧原型月龄推导 |
| 女儿与伙伴 CharacterState | 16 项 A、装备 ID、功法 ID、永久解锁；女儿另有持续压力 | 共享基础结构；伙伴不含独立等级或经验，也不默认增加伙伴压力系统 |
| 父亲恢复状态 | 已完成恢复节点、对应境界表现、下一项恢复目标 | 与女儿成长阶段独立；可由剧情进度推导，不另建耗精力修炼系统 |
| 关系与叙事状态 | 各伙伴好感、亲情关系状态、真相、复仇、心魔 | 与装备、战斗成长分开；字段形式未定的不先造数值条 |
| 回合安排 TurnPlan | 自由精力、冒险已用次数、本回合地图种子记录、培养槽数、有序日程草稿 | 培养槽不是精力；确认后草稿冻结 |
| 库存 Inventory | 物品 ID 到非负数量、灵石 | 共享真库存；预测产出不写入此处 |
| 洞天 CaveState | 已开放区域、入口、道路、建筑实例、御灵实例 | 土地、图纸与故事进度分别管理 |
| 建筑实例 BuildingInstance | 实例 ID、建筑定义 ID、位置、等级、配方 ID | 同类建筑可有多个实例；无独立施工倒计时 |
| 御灵实例 SpiritInstance | 实例 ID、定义 ID、入住状态、工作建筑 ID | 一只至多一份工作；收藏与入住分开 |
| 解锁状态 UnlockState | 已有图纸、功能、目的地、日程、称号等 ID | 功能解锁不等于故事完成；记录下一回合生效的解锁 |
| 剧情进度 StoryState | 已激活节点、完成节点、必要选择、互斥记录 | 一个逻辑主线节点只完成一次 |
| 冒险状态 AdventureState | 目的地、种子或地图、当前位置、已访问节点、队伍生命、战利品领取状态 | 已开始的地图不可因读档无条件重生成 |
| 战斗状态 BattleState | 参战属性快照、生命、效果、技能冷却、物品冷却、全局冷却 | 战斗运行时；是否支持战中存档待定 |
| 结算摘要 SettlementResult | 培养结果、资源变动、剧情解锁、必要完成标记 | 供界面展示，不是一套事件溯源日志平台 |
| 结局结果 EndingResult | 人生结局 ID、结缘结果 ID 或空、成就结果 | 关系结果可缺省，不与人生结局强行二选一 |

御灵工作归属建议只以御灵的工作建筑 ID 为真值，建筑工作槽列表按该关系生成，避免双边列表不一致。若以后因性能缓存，也必须有唯一更新入口。

装备目前只需要定义属性与槽位，不因实体表而新增耐久、品质洗练或装备实例随机词条。

## 4. 配置定义提案

| 配置族 | 最小内容 | 不自动扩展的部分 |
|---|---|---|
| 回合与成长 | 阶段长度、精力规则、槽位与继承成本 | 不默认恢复旧月份和年龄显示 |
| 培养与自由活动 | 类别、解锁条件、成本、基础成长、压力变化 | 不为每项活动写独立脚本 |
| 压力规则 | 区间、概率、倍率、取整方式 | 不增加可视化概率编辑器 |
| 建筑与配方 | 分类、占地、成本、工作槽、投入产出 | 不增加施工、物流运输模拟 |
| 景观与御灵 | 适用对象、词条、距离参数、场景适应性 | 不引入额外等级经验 |
| 物品与装备 | 类别、属性、目标、效果、冷却 | 复杂效果只实现已使用的种类 |
| 角色与功法 | 初始属性、槽位配置、成长奖励、解锁来源 | 不做通用秘籍熟练度树 |
| 剧情 | 检查阶段、前置、条件、互斥、成本、奖励、三阶段表现 | 不做三套逻辑节点或全能脚本语言 |
| 冒险与战斗 | 目的地、节点权重、敌人、套组、掉落、种子策略 | 不做面向玩家的地图编辑器 |
| 结局与成就 | 条件、优先级、互斥、继承选项 | 不从旧 GDD 导入未经确认的名单 |
| 比赛 | 季节、技艺、资格、计分、奖励、轻量玩法参数 | 不预建复杂小游戏插件市场 |

这些配置族是内容归属，不要求现在就创建所有空文件。先为主体闭环用到的内容建表，再随实际内容拆分。

## 5. 几条关键实体关系

### 5.1 A、B 与消费口径

CharacterState 保存 A 和已装备物品引用。属性计算函数根据装备定义生成 B：

- 剧情条件查询 A。
- 比赛查询 A+B。
- 战斗根据已确认公式生成战斗属性，公式暂不在这里假定。
- 真 Boss 在正式确认点读取 A，另套自身配置。

四维总和可从 16 项细分生成，不同时维护两份可独立写入的成长数据。

### 5.2 生产与资源

建筑定义和配方说明“可做什么”，建筑实例记录“本回合安排做什么”。库存只说明“现在实际有什么”。

生产计划需要基于进入生产阶段时的真实库存，统一决定投入、消耗和各建筑输出。不能遍历一栋就把产出加入可供下一栋消耗的库存，否则结果会依赖建筑遍历顺序并违反跨回合加工规则。

建议处理为：冻结本批次输入视图 -> 按最终确定的缺料规则分配投入 -> 计算全部产出 -> 统一提交净变动 -> 再运行主线升级检查。

投入竞争规则未定，因此这里先确定批次边界，不假定所有配方都能成功执行。

产出结构可预留基础产出、御灵乘区、景观词条乘区的分项，供预测与实算共用。御灵数值到倍率的映射、距离函数、数值取整待定后再实现，不凭空指定数值。

### 5.3 图纸、空间与剧情

图纸 ID、开放区域 ID、剧情完成节点分别保存。剧情升级定义把以下内容区分开：

- 剧情前置和关键 Boss 条件。
- 本次尚未获得的经济功能。
- 与这些经济功能对应的资源成本。
- 下一回合生效的奖励。

检查当前局已经继承的功能后，再决定实际经济升级成本，不能用“剧情未完成”推断所有解锁都还要购买。具体多项解锁的成本拆分表需内容设计确认。

### 5.4 剧情节点与三阶段表现

逻辑节点持有稳定 ID、条件、成本、奖励和完成状态；表现部分按三个成长阶段引用对话和立绘。

推进故事时选择当前适用版本，完成后只记同一个逻辑 ID。检查阶段变化不能再次触发已经结算的节点奖励。

## 6. 最少的职责划分

| 职责 | 做什么 | 落地方式 |
|---|---|---|
| 本局状态 | 保存角色、库存、回合与进度，提供唯一真值 | 一个集中状态入口即可；名字和是否 Autoload 按实现决定 |
| 玩法规则 | 执行日程、生产、剧情等已确定规则 | 先写直接可读的函数，有真实复杂度再按玩法拆脚本 |
| 场景交互 | 展示、选择、提交操作、播放反馈 | 使用普通 Godot 场景与对应脚本 |
| 配置与保存 | 加载已使用配置，保存批准边界内的状态 | 少量读写函数和必要校验，不建额外框架 |

这些是代码需要分清的事情，不是四个必须建立的架构层。界面刷新不能扣资源或发奖；预测和结算共用规则；回合确认不能重复执行。满足这些约束即可，不预先规定管理器数量。

## 7. Godot 常规目录

保留项目目前的简单顶层结构。本轮不移动或重写场景、脚本，不创建未来可能用到的空目录。

| 路径 | 放什么 |
|---|---|
| project.godot | Godot 项目设置、主场景与确实需要的全局配置 |
| scenes/ | 实际使用的 .tscn 场景，例如主界面、洞天、对话、战斗 |
| scripts/ | 实际使用的 .gd 脚本，包括场景逻辑、必要的共享规则与保存读取 |
| assets/ | 图像、音频、字体等素材 |
| data/ | 活动、建筑、配方、物品、剧情等可调整配置 |
| docs/ | 主体规则、交互、实体、待决与实施顺序 |

文件增多后再按角色或玩法添加必要子目录。现在不预设 scripts/rules、scripts/services 等架构层目录，也不因写了实体表就生成对应空脚本。

测试可继续使用少量 Godot 测试场景和脚本，不为了辅助玩法单独搭测试项目。现有 smoke_test 的规则已过时，后续按新主体规则替换，不把保留旧断言作为要求。

## 8. 旧原型的参考边界

现有工程经只读检查确认：

- GameState 使用 96 个月、年龄递增、四项聚合属性、父女经验条与数值心魔。
- ScheduleManager 使用同一精力槽执行父女活动、重复收益递减、主动破境和立即产出。
- Main 通过代码建立单屏 UI，当前行动队列不等于新规则的固定培养槽。
- smoke_test 验证的是旧精力和父亲筑基流程，不能沿用成功输出证明新设计正确。

上述实现只用于了解当前原型，并不决定新设计怎样写。后续以新主体规则为准，可以直接重写有关脚本与场景，不安排单独的旧架构迁移工程。

不要求兼容旧原型存档，也不要求保留旧文件名和单例注册。需要保留的是清晰的 Godot 目录与可读实现，而不是生成代码的历史结构。未经新一轮开发确认，本次不实际删除或覆盖旧代码。
